# 经验教训（Lessons Learned）

复发问题的暂存区：记录 reviewer 反复退回的同类问题与 Agent 常犯的坑，让同一个坑不踩第三次。本文档是规范的**候选池**——条目在这里验证价值，稳定后升格，不在这里长住。

## 收录准入

- **同类问题第二次出现才收录**——单次偶发不收，防噪音。
- 来源：reviewer 退回报告、交回物的 known gaps、用户纠偏。
- 不收待办（走任务卡）；不收项目常识（进 `standards/` 或 feature 文档）。

## 条目格式

一条 lesson 一个小节，新条目加在「条目」节最上方（倒序）：

    ### <一句话规避规则>
    - 日期：YYYY-MM-DD
    - 现象：踩了什么坑、复发几次
    - 根因：为什么会发生
    - 规避：怎么做能不再犯（可验证的行为，不是口号）
    - 来源：reviewer 报告 / known gaps / 用户纠偏（附提交或任务标识）

## 升级路径

某条 lesson 被稳定复用（约第三次引用起）→ 升格为 `knowledge/standards/` 规则或 `rules/` 红线，原条目标注「已升格 → <落点>」，保留不删。

## 条目

### 新判据必须在**同一提交内**配一个能让它变红的反例——反例是判据自身的第一个读者,不只是防回归

- 日期：2026-08-29
- 现象：同一批交付里连犯三次,每次都是「写下了判据,却没有按判据构造的失败用例护航」。① 给 durable 键加 schemaId 命名空间时,注释里写着「不让内容不同的记录互相夺舍」,却只给 WAL 加了前缀、Txn/Command 没加——**同一提交内就违反了自己刚写的规范**,后果是同键的 Command 被 Txn 静默夺舍并返回 `Accepted`。② 向 TD 报「拼接键单射依赖三条前提」,其中「没有 schemaId 是另一个的前缀」根本不是必要条件;写守护测试时才发现那条检查分支**测不红**——能触发它的输入必然含分隔符,而含分隔符的检查排在它前面,故**实际不可达**。③ 改口后把「分隔符之前的字段不含分隔符」当作**充分**条件,仍错:分隔符若自重叠(如 `"::"`),`("a", ":b")` 与 `("a:", "b")` 同拼成 `"a:::b"`,两者都满足该条件。而当时新增的 6 条守护对分隔符宽度**零断言**——把常量改成 `"::"`,守护**全绿**。
- 根因：判据是用推理写出来的,而推理**不会告诉你它漏了哪一维**。三次都是同一形状:判据成立的那些维度被反复检查,判据**失效**的那一维从未被构造过。第 ① 次是漏了一半输入类型,第 ②③ 次是漏了一整个自由度(分隔符本身)。人在写判据时天然只想着「怎样算对」,不想「怎样能让它错」。
- 规避：
  1. **每写一条判据,同一提交内必须有一个「让它红」的用例**,且该用例要沿判据**可能失效的那一维**变化,而不是沿它显然成立的那一维。上面 ③ 的 6 条对抗性记录键全部只在「分隔符之后」变化——而按正确的数学,那一维**永不影响单射**,所以它们构造上不可能失败,是装饰不是守护。
  2. **判据写错过一次,就别再只查判据——直接查结论。** 前提清单可以写错(本次写错两次),「单射」这个结论查不了假:穷举拼接结果找重复即可。查结论的测试对「你靠哪条不变量活着」不敏感。
  3. **凡是自己新造的旋钮(提成 const 的分隔符、可配的宽度、可替换的策略),守护必须对该旋钮的取值有断言**。本次把 `KeySeparator` 提成 `internal const` 的同一个提交,却没有任何测试钉住它的合法取值范围——亲手造了旋钮又不给它上锁。
  4. **借来的性质要写明借条**:若某性质来自数据的偶然形态(id 里恰好没有分隔符)而非编码保证,就在守护里写清它靠什么活着,并让上游改动时**这里先红**。
  5. **报守护有效性的数字必须 like-for-like,并写明口径**。本批同一个坑踩了两次:① CS8669 记成「92 处」(实为 23 处 × 2 TFM × 2 次重复);② 报「守护全绿 → 4 条红」,而 like-for-like 是「守护 0 红 → **1** 红」——另 3 条红是别处的字面量键钉,对**任何**分隔符改动都会红(含无害的 `"ab"`),根本不守那条前提。**两次都朝同一个方向偏**。这与本文件已收录的「计数随 additive 增补腐烂」不是一回事:那条是**中性的时间效应**,这条是**有方向的偏差**——同一个人报自己的工作,取的口径会系统性地让改动显得更有效。防法也不同:前者靠改存在性 / 身份断言,后者只能靠**声明口径**(比的是哪两个版本、红的分别落在哪个测试类)加**别人复跑**。凡是「X 个 → Y 个」形式的有效性声称,先问一句:两边是同一把尺子吗?
- 来源：R-00138(T05)S06 交付与其两轮 reviewer 退回报告(P0-1 / P1);本仓 `590b463`、PR LumioGames/LumioGameRuntime#8;TD 会话 lumiogameenginearchitecture-b3 的跨仓裁决(同族问题在 LumioServer 的两处闸门哈希上确认为实际缺陷)。

### 跨工具的默认值落差在**产生方不可见、消费方致命**——升级依赖面时,先单独构建每个消费项目,别信「测试全绿」

- 日期：2026-08-29
- 现象：把 generated 面重 pin 到架构源新基线(`5f06822` → `a206e2c`)时，同一次交付里连撞两个同类坑，两个都**在上游侧完全不可见**。① 上游生成器在 `// <auto-generated />` 文件里发射可空注解却不发 `#nullable` 指令；编译器对 auto-generated 文件停用项目级可空上下文，于是 **23 处**注解全部告警——上游自己的 csproj 开了 `Nullable` 但没开 `TreatWarningsAsErrors`，所以上游只看到警告，本仓看到的是错误。(**这个计数本身是本条教训的又一个实例**:构建日志里 CS8669 有 92 行，第一版记录直接写了「92 处」，虚高 4 倍——去重 `file:line:col` 才是 23 处，92 = 23 × 2 个 TFM × 2 次重复报告。日志行数不是站点数，写进常驻知识库前先 `sort -u`。)② 本仓 `.gitignore` 的 `artifacts/`(原意是忽略仓库根的 SBOM/依赖报告输出)在大小写不敏感的文件系统上同时匹配生成物目录 `src/…/Generated/Artifacts/`，新基线新增的 5 个生成文件因此被**静默**忽略、`git status` 里根本不出现。第二个坑还叠了第三层:`dotnet run --project <测试项目>` 只解析测试项目 TFM(`net10.0`)那一份 ProjectReference 资产，生产项目的 `netstandard2.1` 目标**根本没被编译**——`modules/observability` 就这样带着 `System.Threading.Channels` 在该 TFM 不可用的硬错误(源自 `0754da8`)通过了 19/19，直到单独 `dotnet build` 该生产项目才暴露。
- 根因：三者共享一个病理——**判断依据在「产生方」与「消费方」之间存在默认值落差，而失效是静默的**。上游按自己的编译策略看不到问题；`.gitignore` 的匹配语义随文件系统大小写敏感性变化；测试命令的构建闭包小于项目的声明闭包。三处都表现为「看起来验证过了」，其中第二处更危险:本机闸门比对文件系统会误绿，只有 CI 全新 checkout 才会因缺文件报 `GENERATED_CONTRACT_DRIFT`——**本机绿、CI 红，且本机的提交必然残缺**。
- 规避：
  1. **升级任何依赖/生成面之后，对每个生产 csproj 单独 `dotnet build`**，不要用「测试全绿」代替。测试项目单目标时，多目标生产项目的破损不会进测试的构建闭包。
  2. **忽略规则一律锚定**:`/artifacts/` 而不是 `artifacts/`。未锚定的目录名会在任意深度匹配，且在大小写不敏感的文件系统上连大小写不同的目录一起吞。新增生成文件后必须 `git status --untracked-files=all` 确认它们真的出现，`git check-ignore -v <路径>` 是判定归属哪条规则的唯一可靠手段。
  3. **怀疑某个失败是不是自己引入的，就建对照 worktree 而不是推理**:`git worktree add --detach <tmp> <未含改动的 commit>` 跑同一条命令。本次据此在 10 分钟内把 netstandard2.1 失败定性为 `0754da8` 遗留的既有缺陷，避免了在自己的 PR 里顺手修一个属于别人范围、且需升级确认(改目标框架 / 加包)的问题。
  4. **消费侧的权宜抑制必须写清偿还条件**:本次 `NoWarn CS8669` 注明「上游改为发射 `#nullable enable` 后必须删掉」，并把代价(generated DTO 对消费方 nullable-oblivious)写在同一处。不写偿还条件的抑制会变成永久债。
- 来源：R-00138(T05)重 pin 交付与其 known gaps;本仓 `0da2f12` / PR LumioGames/LumioGameRuntime#6;既有缺陷来自 `0754da8`。

### 闸门的判据必须锚定不可变对象的**原始字节**，闭合到哪一步就只声称到哪一步，并用对照组探针证明它真的会响

- 日期：2026-08-29
- 现象：`eng/verify-generated-contracts.*` 从架构源仓的**工作区**重新生成再比对，而该仓被多个会话并发编辑，闸门结论随之漂移（实测其发布 identity 一天内变四次，`origin/main` 单次会话内前移三次）。更早一次（`4dfc00e` → 10 分钟后被 `66a71b0` revert）已踩过同一个坑。修复时改为按 commit 用 `git archive` 只读物化——**看似解决了，实则只是把移动靶的轴从「什么时候跑」换成了「在哪台机器上跑」**：架构源 `.gitattributes` 第一行是 `* text=auto`，`git archive` 会按调用方的 `core.autocrlf` 做行尾转换，同一个 commit 在 Windows 默认配置下导出的字节与 Linux/macOS 不同。审查阶段实测：用 `core.autocrlf=true` 导出再跑生成器，拿到的正是被当成「伪造」而修掉的那组旧值——五个溯源戳里**四个是同一 commit 在 Windows 上的忠实渲染，根本不是伪造**（只有 `compilerHash` 是真的读了脏工作区）。差一点就以「修正虚假 provenance」的名义把一组诚实的值改掉，并把错误根因写进 ADR。
- 根因：两层，第二层更隐蔽。① 判据引用了可变来源（他仓工作区）；② 判据哈希的是**经 attribute 转换后物化的字节**，而不是 git 对象本身——于是即使锚定了 commit，判据仍是 `(commit, 机器配置)` 的函数。共同的病理是把「看起来在守护的东西」当成「在守护」，且失效**静默**：闸门照常输出绿色。第三种形态同样在场：`.github/workflows/repository-policy.yml` 至今**没有调用** `eng/verify-dependencies.sh` / `eng/generate-sbom.sh` / `eng/verify-generated-contracts.sh`——脚本写得再全，不在准入路径上就等于不存在。
- 规避：
  1. **判据只引用不可变对象，且要取到它的原始字节**：比对基准是 git 对象/已发布 artifact 的哈希。`git archive` 至少要带 `-c core.autocrlf=false -c core.eol=lf -c core.attributesfile=<空文件>`（**属性优先于配置**，全局 `~/.gitattributes` 一行 `* eol=crlf` 就能把前两个压过去）；验证办法是与 `git cat-file blob <commit>:<path>` 比对。跨仓只读物化用 `git archive` 不用 `git worktree add`（后者会往对方 `.git` 写注册记录）。
  2. **闭合到哪一步，就只声称到哪一步**。上述三个开关堵住的是配置通道；`$GIT_DIR/info/attributes` 没有任何 config 开关，`filter` smudge 也仍会被 archive 应用——所以准确说法是判据为 `(commit, attribute 栈)` 的函数，**不是** `commit` 的纯函数。真要闭合就直接哈希 blob，绕开整条转换链。把「看起来闭合的」写成「已闭合的」，正是本条教训要治的病，写文档时会不自觉地复发。
  3. **锚点解析失败即失败**，不得回落到工作区（`ARCHITECTURE_COMMIT_MISSING` / exit 31）。静默回落是第一层的根。
  4. **硬 gate 与报告项分开**：会随上游变动的判断做成报告、不 fail；只有确定性判据才配决定退出码。参见 [`../decisions/0002-generated-contract-gate-anchors-committed-objects.md`](../decisions/0002-generated-contract-gate-anchors-committed-objects.md)。
  5. **交付前用对照组探针证伪，而且探针要打在「判据本身会不会变」上，不只打在「违规会不会被抓」上**：本次抓住第二层靠的是「注入 `core.autocrlf=true` 再跑一遍，看结论动不动」——只测「改坏了会不会报错」永远发现不了它。**只读配置不算探针**：本次曾 `grep export-ignore` 后判定 `.gitattributes` 无害，却没读它第一行的 `* text=auto`，正是同一种错误的自我复现。
- 来源：R-00131（T03）交付与其 reviewer 退回报告（P0-1）；本仓 `4dfc00e` / `66a71b0` 的先例；总调度跨仓通报（LumioClient / LumioServer 各自独立踩中 BannedApiAnalyzers 因文件名不匹配而整份禁令静默失效）。
